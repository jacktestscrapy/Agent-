# 第4章 工具调用与能力扩展模式

> 本章目标：理解 Agent 如何安全地使用外部能力，掌握 Tool-Use、Function Calling、Tool Registry 与 MCP 的职责边界，并能实现受约束、可验证、可扩展的工具调用流程。

前几章讨论了 Agent 的基本组成、固定工作流和动态决策。本章进一步解决一个关键问题：Agent 如何从“能够生成回答”扩展为“能够依据明确接口使用外部能力”。

本章围绕四个主题展开：

1. **Tool-Use**：Agent 选择并调用程序提供的工具。
2. **Function Calling**：模型以结构化格式提出函数调用请求，应用负责校验和执行。
3. **Tool Registry**：应用登记、描述、查找和调度可用工具。
4. **MCP**：通过通用协议连接 Agent 应用与外部工具/上下文服务器。

## 4.1 为什么 Agent 需要工具

语言模型擅长理解、归纳和生成，但模型本身并不天然具备实时查询、访问业务系统、执行计算或读取私有数据的能力。工具为 Agent 提供受控的外部能力，例如：

| 工具 | 示例用途 | 典型风险 |
|---|---|---|
| 知识库检索 | 查询内部文档 | 检索结果可能包含不可信指令 |
| 业务查询 | 查看订单或工单状态 | 越权读取、隐私泄露 |
| 计算工具 | 汇总指标或换算单位 | 输入边界和精度错误 |
| 写入工具 | 创建工单或发送通知 | 重复执行、不可逆副作用 |

Tool-Use 的核心不是让模型直接执行代码，而是让模型从应用明确提供的能力中提出调用意图，由可信的程序校验参数、检查权限、执行工具，再把结果作为观察反馈给模型。

## 4.2 Tool-Use 的执行闭环

一个典型工具调用包含以下步骤：

1. 应用向模型提供用户任务和可用工具描述。
2. 模型返回普通文本，或提出一个/多个结构化工具调用。
3. 应用验证工具是否存在、参数是否符合契约、调用者是否有权限。
4. 应用执行允许的工具，并记录结果、耗时和调用身份。
5. 应用将工具结果附在对应调用上，再请求模型继续处理。
6. 模型整合观察结果，或提出下一次调用；应用执行次数和预算达到上限时停止。

~~~mermaid
sequenceDiagram
    participant U as 用户
    participant H as Agent 应用
    participant L as 语言模型
    participant R as Tool Registry
    participant T as 工具
    U->>H: 任务
    H->>L: 任务 + 工具描述
    L-->>H: 工具名 + 结构化参数
    H->>R: 查找工具并校验
    R-->>H: 已登记的工具定义
    H->>T: 执行（权限/预算校验后）
    T-->>H: 结果或明确错误
    H->>L: 工具结果
    L-->>H: 最终回答或下一次工具调用
    H-->>U: 回答
~~~

模型返回调用请求不代表工具已经执行，也不代表请求可信。工具执行权始终在应用程序一侧。

## 4.3 Function Calling：结构化调用请求

Function Calling（也常称 Tool Calling）是模型 API 的一种交互能力。应用提供函数名称、用途及参数 Schema，模型可以在响应中返回结构化调用请求。应用读取请求并调用本地函数，再把结果关联到原始调用 ID 后继续对话。

需要区分三个概念：

- **工具定义**：描述工具的名称、说明和参数结构。
- **模型调用请求**：模型产生的候选动作，仍需应用校验。
- **工具执行结果**：应用实际运行后产生的返回值。

简单示意：

~~~python
# 将只读知识检索工具描述为模型可识别的函数，并声明中文输入字段。
# 工具标识符遵循接口命名约束，描述内容和示例参数使用中文。
tools = [{
    "type": "function",
    "function": {
        "name": "search_knowledge",
        "description": "在本地教学知识库中搜索内容",
        "parameters": {
            "type": "object",
            "properties": {"查询内容": {"type": "string"}},
            "required": ["查询内容"],
            "additionalProperties": False,
        },
    },
}]
~~~

完整往返示例见 `examples/chapter04/function_calling_agent.py`。示例使用 DeepSeek 的 OpenAI 兼容接口；不同模型和 SDK 的工具调用支持、参数约束及响应字段可能不同，应以所用服务的文档为准。

### 4.3.1 参数校验与失败处理

应用至少应检查：

- 工具名是否在当前允许列表中。
- 参数是否为合法 JSON 对象。
- 必填字段是否存在，是否出现未声明字段。
- 参数类型、范围、长度和业务约束是否有效。
- 当前用户和当前任务是否有权执行该操作。

拒绝无效请求时，应将明确的工具错误结果返回给模型或调用者，并保留可观测记录；不要把校验失败伪装成成功，也不要静默改写参数。

## 4.4 Tool Registry：统一的工具登记与分发

当工具很少时，可以直接用字典映射模型返回的名称和 Python 函数。随着工具数量、权限和不同 Agent 的增加，分散的映射容易造成名称不一致、重复实现和权限边界不清。

Tool Registry 将工具定义集中管理，通常负责：

- 为工具分配稳定名称和说明。
- 管理输入 Schema 与执行函数的对应关系。
- 生成模型所需的工具描述。
- 在执行前统一做名称与参数校验。
- 按调用者、任务或租户筛选可见工具。
- 记录调用、结果、错误和运行指标。

Registry 不应成为绕过权限的万能入口。工具列表应按最小权限原则提供；高风险工具需要独立授权、人工确认、幂等键和审计记录。示例 `tool_registry.py` 使用一个轻量注册表展示这些基础职责。

## 4.5 MCP：模型上下文协议

MCP（Model Context Protocol）是用于连接 AI 应用与外部能力/上下文的开放协议。它定义了标准化的客户端—服务器交互方式，常见能力包括：

- **Tools**：可由模型请求、由服务器执行的操作。
- **Resources**：应用可读取的上下文资源。
- **Prompts**：服务器提供的可复用提示模板。

典型参与者包括：

- **Host**：承载模型和用户交互的应用。
- **MCP Client**：由 Host 管理、负责连接一个 MCP Server 的协议客户端。
- **MCP Server**：通过 MCP 暴露工具、资源或提示的服务端。

MCP 标准化的是能力发现和调用的交互协议，不会自动替应用完成用户授权、租户隔离或业务安全策略。MCP Server 暴露的工具仍然需要按外部 API 一样进行威胁建模和权限控制。

~~~mermaid
flowchart LR
    U[用户] --> H[Agent Host]
    H --> L[模型]
    H --> C[MCP Client]
    C <-->|MCP 协议| S1[MCP Server: 知识库]
    C <-->|MCP 协议| S2[MCP Server: 工单]
    S1 --> D1[(文档数据)]
    S2 --> D2[(业务系统)]
~~~

Function Calling 和 MCP 不是互相替代的技术：

| 维度 | Function Calling | MCP |
|---|---|---|
| 解决的问题 | 模型如何表达结构化工具调用意图 | 应用如何以标准协议发现并连接外部能力/上下文 |
| 主要交互双方 | 模型 API 与调用它的应用 | MCP Host/Client 与 MCP Server |
| 执行责任 | 应用校验并执行函数 | MCP Server 执行所暴露的能力；Host/Client 管理连接 |
| 是否负责用户权限 | 否 | 否 |
| 常见组合 | 模型请求调用 Registry 中的工具 | Host 从 MCP Server 发现工具，再将适用工具提供给模型 |

本章 `mcp_server.py` 与 `mcp_client.py` 使用官方 Python SDK 展示本机 stdio 通信。示例工具只返回教学用数据，不连接真实业务系统。

## 4.6 工具安全与可靠性

工具调用会把模型输出转变为真实程序行为，因此需要将“模型可以建议什么”和“应用实际允许什么”分开：

1. **最小权限**：只向当前任务提供所需工具；默认拒绝未登记的调用。
2. **输入校验**：按 Schema 和业务规则验证参数，限制长度、范围和资源消耗。
3. **区分只读与写入**：写入、发送、删除、付款等副作用操作需更严格的授权与确认。
4. **抵御提示注入**：把工具返回内容视为数据而不是新的系统指令；不要让检索文本改变工具权限。
5. **防止重复副作用**：使用幂等键、去重或显式确认；重试不能默认等于安全重放。
6. **控制预算**：限制并发、单次任务调用数、超时、响应体大小和成本。
7. **安全处理错误**：向模型提供足够的可恢复信息，不泄露凭据、堆栈或内部敏感数据。
8. **审计与可观测性**：记录调用者、工具名、参数摘要、授权决策、耗时和结果状态；避免记录不必要的敏感内容。
9. **MCP 边界**：校验服务器身份和传输方式；仅连接可信服务器；对每个服务器提供的能力单独授权。

## 4.7 模式选择与组合

| 场景 | 建议 |
|---|---|
| 少量稳定的本地工具 | 简单的显式映射即可 |
| 多个 Agent 共用工具，需统一校验与权限 | 使用 Tool Registry |
| 模型 API 支持结构化工具请求 | 使用 Function Calling，并由应用执行工具 |
| 不同 Host 需要连接多个标准化能力服务 | 考虑 MCP |
| 高风险写操作或不可逆业务动作 | 加入授权、人工确认、审计和幂等控制 |
| 流程固定且工具选择不需要动态决定 | 直接使用 Workflow，不必引入 Agent 工具循环 |

实际系统经常组合这些模式：MCP 客户端发现外部能力，应用把经过授权筛选的工具定义交给模型，模型通过 Function Calling 提出请求，Registry 做统一校验与本地调度，最后应用记录结果并决定是否继续。

## 4.8 运行示例

在仓库根目录安装依赖：

~~~bash
pip install -r requirements.txt
~~~

本地注册表示例无需 API Key：

~~~bash
python examples/chapter04/tool_registry.py
~~~


~~~bash
python examples/chapter04/mcp_client.py
~~~

## 4.9 本章小结

- Tool-Use 是 Agent 通过外部工具扩展能力的模式；程序而非模型负责最终执行。
- Function Calling 提供结构化调用请求，但不等于验证、授权或执行。
- Tool Registry 为工具定义、发现、校验和调度提供应用内的统一边界。
- MCP 标准化 Host/Client 与 Server 之间的能力交互，但不取代业务权限和安全控制。
- 工具能力越强，越需要最小权限、参数校验、预算、幂等、人工确认和审计。
