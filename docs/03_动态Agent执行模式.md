本章承接第二章的基础 Workflow 设计模式，开始进入真正具有动态决策能力的 Agent 执行机制。

第二章学习的是：开发者提前设计好流程，由程序决定每一步执行什么。

第三章学习的是：当任务执行路径无法完全预先确定时，如何让 LLM 根据当前任务、执行状态和环境反馈，动态决定下一步行动。

本章重点讲解三种模式：

1. **ReAct**：通过推理、行动和观察循环完成任务。
2. **Plan-and-Execute**：先制定任务计划，再逐步执行和调整。
3. **Reflection**：通过自我反思、评估和修正改善结果质量。

# **第3章 动态 Agent 执行模式**

## **3.1 为什么需要动态 Agent 执行模式**

### **3.1.1 Workflow 的局限性**

第二章介绍了 Prompt Chaining、Routing 和 Parallelization 三种基础工作流模式。

这些模式适用于流程相对明确的任务。

例如，企业内容生产助手：

用户输入主题生成文章大纲撰写文章润色文章输出结果

整个执行过程由开发者提前定义。

但是，假设用户提出以下任务：

> 帮我分析某家企业最近的发展情况，结合行业趋势、竞争对手和最新公开信息，最后给出一份分析报告。

这个任务存在几个问题：

- 需要查询的信息不确定。
- 不同企业需要查询的资料不同。
- 某些资料可能需要进一步验证。
- 查询结果可能引出新的问题。
- 分析过程中可能需要调整原来的分析方向。

如果采用固定 Workflow，开发者需要提前定义所有可能的执行路径。

这会导致两个问题：

1. 流程越来越复杂，维护成本越来越高。
2. 遇到未预设的情况时，系统无法灵活调整执行过程。

此时就需要引入动态 Agent。

### **3.1.2 什么是动态 Agent 执行模式**

动态 Agent 执行模式是指：在任务执行过程中，由 LLM 根据当前任务状态、上下文和已有观察结果，动态决定下一步执行动作。

典型流程：

接收用户目标理解当前任务LLM动态决策下一步执行什么执行工具观察执行结果更新任务状态输出结果请求补充信息或人工介入调用工具继续分析任务完成无法完成

与第二章 Workflow 相比，动态 Agent 最重要的变化是：

**执行路径不再完全由开发者预先定义，而是允许模型根据执行过程中的信息动态调整。**

### **3.1.3 Workflow 与动态 Agent 的区别**

| 对比维度 | Workflow | 动态 Agent   |
| ---- | -------- | ---------- |
| 流程设计 | 开发者预先定义  | 模型根据任务动态决策 |
| 执行路径 | 相对固定     | 可以动态变化     |
| 工具选择 | 通常由程序指定  | 可以由模型选择    |
| 任务拆分 | 通常提前定义   | 可以动态拆分     |
| 结果反馈 | 按固定流程处理  | 根据观察结果调整   |
| 可预测性 | 较高       | 相对较低       |
| 调试难度 | 相对容易     | 需要跟踪决策过程   |
| 成本控制 | 较容易      | 需要设置执行预算   |
| 适用任务 | 稳定、重复的业务 | 路径不确定的复杂任务 |

需要注意：

动态 Agent 并不意味着完全放弃程序控制。

在企业级应用中，比较合理的方式是：

- LLM 负责任务理解、行动选择和结果判断。
- Python 程序负责工具执行、状态管理和权限校验。
- 开发者负责设置执行边界、预算和停止条件。

## **3.2 ReAct：推理与行动模式**

### **3.2.1 什么是 ReAct**

ReAct 是 Reasoning and Acting 的缩写，中文通常称为推理与行动模式。

该模式的核心思想是：

让模型在任务执行过程中交替进行推理和行动，并通过观察行动结果决定下一步。

ReAct 不是简单地让模型先思考，再调用一次工具，而是形成一个持续循环：

**Reason → Act → Observe → Reason**

例如用户提出：

> 北京今天的天气怎么样？如果下雨，提醒我带伞。

Agent 可能按照以下过程执行：

| 步骤 | 执行动作     | 结果          |
| -- | -------- | ----------- |
| 1  | 理解用户需求   | 需要查询北京天气    |
| 2  | 选择天气查询工具 | 调用天气 API    |
| 3  | 观察工具结果   | 发现今天有降雨     |
| 4  | 决定下一步    | 提醒用户带伞      |
| 5  | 输出结果     | 今天有雨，出门记得带伞 |

这里的关键在于：模型根据天气工具的实际返回结果决定下一步，而不是提前写死所有处理逻辑。

### **3.2.2 ReAct 的核心组成**

ReAct 通常包含四个核心环节。

**1. Reason：推理**

模型分析当前任务和已有信息，判断下一步需要做什么。

例如：

- 当前信息是否足够？
- 是否需要调用工具？
- 应该调用哪个工具？
- 是否需要继续执行？

**2. Act：行动**

模型选择一个行动，并生成相应的工具调用请求。

例如：

- 搜索网页。
- 查询数据库。
- 读取文件。
- 调用业务 API。
- 执行 Python 函数。

需要强调：模型只是提出工具调用请求，真正执行工具的是应用程序。

**3. Observe：观察**

应用程序执行工具，并将结果返回给模型。

例如：

```
{
  "tool": "weather_query",
  "status": "success",
  "result": {
    "city": "北京",
    "weather": "小雨",
    "temperature": "12℃"
  }
}
```

**4. Continue / Finish：继续或结束**

模型根据观察结果判断：

- 是否已经完成任务。
- 是否需要继续调用工具。
- 是否需要更换执行策略。
- 是否应该停止并向用户说明限制。

### **3.2.3 ReAct 执行流程**

用户提出任务构建上下文LLM分析任务是否需要工具生成工具调用请求程序执行工具返回Observation更新Agent状态是否完成输出最终答案需要不需要是否

ReAct 的特点是没有要求模型必须提前规划全部步骤。

模型可以在每一轮中，根据最新的 Observation 重新决定行动。

### **3.2.4 ReAct 与普通工具调用的区别**

| 对比维度   | 普通工具调用    | ReAct      |
| ------ | --------- | ---------- |
| 工具调用次数 | 通常一次或预设次数 | 可以多次       |
| 后续决策   | 通常由固定程序决定 | 根据观察结果动态决策 |
| 执行过程   | 相对简单      | 循环执行       |
| 工具选择   | 通常预先指定    | 可以动态选择     |
| 适用场景   | 简单查询、固定业务 | 多步骤探索和问题处理 |

例如：

用户问：“帮我检查项目为什么启动失败。”

普通工具调用可能只读取一次日志。

ReAct Agent 则可能：

1. 读取启动日志。
2. 发现数据库连接失败。
3. 检查数据库配置。
4. 发现数据库地址配置错误。
5. 检查配置文件中的连接地址。
6. 输出故障原因和修复建议。

示例文件规划：

- `search_knowledge`：查询本地知识库。
- `get_product_info`：查询产品信息。

### **3.2.6 ReAct 的优点与局限**

优点：

1. 执行路径灵活，可以根据观察结果动态调整。
2. 能够调用多个工具完成复杂任务。
3. 不需要提前设计所有可能的执行路径。
4. 适合探索性、信息不完整的任务。
5. 能够记录工具调用轨迹，方便分析执行过程。

局限：

1. 多轮调用会增加 Token 消耗和执行延迟。
2. 模型可能选择错误工具。
3. 工具结果可能被错误理解。
4. 可能出现重复调用或循环执行。
5. 最终结果仍然需要验证。

**工程建议：**

ReAct 必须设置最大执行轮数、最大执行时间、工具调用白名单和预算限制。不能让 Agent 无限循环。

## **3.3 Plan-and-Execute：规划与执行模式**

### **3.3.1 什么是 Plan-and-Execute**

Plan-and-Execute 是一种先规划、后执行的 Agent 模式。

它将任务处理拆成两个主要阶段：

- **Plan：规划阶段**，由模型将复杂目标拆解为多个可执行子任务。
- **Execute：执行阶段**，按照任务计划逐项完成工作。

与 ReAct 每次只决定下一步不同，Plan-and-Execute 更强调先形成一个整体执行计划。

例如用户提出：

> 帮我开发一个简单的企业知识库问答系统。

Agent 可以先生成以下计划：

| 序号 | 子任务   | 预期结果           |
| -- | ----- | -------------- |
| 1  | 分析需求  | 明确系统功能和用户角色    |
| 2  | 设计架构  | 确定前后端、数据库和模型方案 |
| 3  | 设计数据库 | 输出数据表结构        |
| 4  | 开发后端  | 实现知识库管理和问答接口   |
| 5  | 开发前端  | 实现文档上传和问答页面    |
| 6  | 测试系统  | 验证主要功能         |

随后 Agent 根据计划逐项执行。

### **3.3.2 Plan-and-Execute 的核心组成**

**1. Planner：规划器**

负责理解用户目标，并生成可执行计划。

规划结果需要尽量明确：

- 子任务名称。
- 子任务描述。
- 执行顺序。
- 前置依赖。
- 完成标准。

**2. Executor：执行器**

负责执行具体任务。

执行器可以是：

- 普通 Python 函数。
- LLM 调用。
- ReAct Agent。
- 外部业务工具。
- 其他专业 Agent。

**3. State：任务状态**

保存当前计划、已完成任务、执行结果和失败信息。

**4. Replanner：重新规划器**

当任务执行失败、环境发生变化或者原计划不再适用时，重新调整后续任务。

### **3.3.3 Plan-and-Execute 执行流程**

接收用户目标Planner生成计划任务计划列表Executor执行当前任务执行是否成功更新任务状态记录错误是否全部完成Replanner调整计划汇总执行结果输出最终结果成功失败否是

### **3.3.4 Plan-and-Execute 与 ReAct 的区别**

| 对比维度 | ReAct      | Plan-and-Execute |
| ---- | ---------- | ---------------- |
| 核心思想 | 边推理边行动     | 先规划再执行           |
| 规划方式 | 通常逐步决策     | 先生成整体计划          |
| 执行方式 | 每轮根据观察调整   | 按任务计划执行          |
| 任务拆分 | 可以动态发生     | 在规划阶段明确拆分        |
| 计划调整 | 每轮重新判断     | 通过 Replanner 调整  |
| 适合任务 | 路径不确定、需要探索 | 目标复杂、步骤较多        |
| 主要风险 | 循环调用、决策不稳定 | 计划不合理、计划过时       |

一个简单的判断方法：

- 如果不知道下一步应该做什么，可以考虑 ReAct。
- 如果已经知道目标，但需要拆解成多个子任务，可以考虑 Plan-and-Execute。

### **3.3.5 Python 实现：任务规划与执行**

示例文件规划：

`examples/chapter03/plan_execute.py`

案例：

> 制定一个企业 AI Agent 项目的开发计划，并模拟执行每项任务。

第一步：规划器生成任务列表。

```
def create_plan(goal):    prompt = f"""    请将下面的目标拆解成可执行任务：    {goal}    返回任务列表，每个任务包含：    id、task、description、status。    """    return ask_deepseek(prompt)
```

第二步：执行器执行任务。

```
def execute_task(task):    prompt = f"""    请完成以下任务：    任务名称：{task["task"]}    任务描述：{task["description"]}    输出具体执行结果。    """    return ask_deepseek(prompt)
```

第三步：执行计划。

```
def run_plan(plan):    results = []    for task in plan:        result = execute_task(task)        results.append({            "task": task["task"],            "result": result        })    return results
```

上述代码用于说明 Planner 与 Executor 的职责分离。正式实现还需要将模型生成的计划解析为结构化数据，并保存任务状态。

### **3.3.6 Replanner：动态重新规划**

实际任务很少能够保证一次规划就完全正确。

例如：

原计划：

1. 查询企业信息。
2. 查询行业信息。
3. 分析竞争对手。
4. 输出报告。

执行第二步时发现行业数据无法获取。

此时不能简单地认为整个任务失败，而应该重新规划：

1. 使用其他数据源查询行业信息。
2. 如果仍然无法获得数据，标记该部分为待验证。
3. 继续执行其他任务。
4. 在最终报告中明确说明数据缺失。

Replanner 的主要职责是：

- 判断失败是否影响后续任务。
- 分析原计划是否需要调整。
- 重新安排任务顺序。
- 删除已经不必要的任务。
- 增加新的补充任务。

### **3.3.7 Plan-and-Execute 的优点与局限**

优点：

1. 复杂任务的整体结构更加清晰。
2. 任务之间的依赖关系更容易管理。
3. 可以跟踪每个子任务的完成情况。
4. 适合长时间运行的任务。
5. 容易扩展为多个执行器协作。

局限：

1. 初始计划可能存在错误。
2. 计划过细会增加规划成本。
3. 环境变化可能导致计划失效。
4. 执行器可能无法正确完成任务。
5. 需要额外维护任务状态和依赖关系。

**工程建议：**

不要将模型生成的计划直接视为可信任务指令。应对计划进行结构化解析、依赖检查、任务范围校验和权限检查。

## **3.4 Reflection：反思与自我修正模式**

### **3.4.1 什么是 Reflection**

Reflection 是通过模型对已有结果进行检查、评价和反思，再根据反馈进行修正的 Agent 模式。

它解决的问题是：

**模型第一次生成的结果不一定足够好，能否通过后续评价和修正提升最终质量？**

例如用户提出：

> 写一份企业级 Agent 技术方案。

模型第一次生成的方案可能存在：

- 缺少系统架构图。
- 没有考虑权限控制。
- 技术选型缺乏依据。
- 没有测试方案。
- 没有说明部署方式。

Reflection 会让模型重新检查自己的结果，并提出改进意见。

### **3.4.2 Reflection 的核心组成**

**1. Generator：生成器**

负责生成初始内容或执行结果。

**2. Reflector：反思器**

负责检查结果，识别问题和不足。

**3. Feedback：反馈信息**

保存反思结果，明确需要修改的内容。

**4. Refiner：修正器**

根据反馈重新生成或修改结果。

### **3.4.3 Reflection 执行流程**

接收用户需求Generator生成初始结果Reflector评价结果是否满足质量要求输出最终结果生成改进意见Refiner修正结果是否

Reflection 可以多轮执行，但必须有最大迭代次数或质量阈值。

### **3.4.4 Reflection 的评价维度**

不同任务需要不同的评价标准。

以技术方案生成为例：

| 评价维度 | 评价内容          |
| ---- | ------------- |
| 完整性  | 是否覆盖全部需求      |
| 正确性  | 技术描述是否准确      |
| 可行性  | 技术方案是否能够实施    |
| 一致性  | 各模块设计是否存在冲突   |
| 安全性  | 是否考虑身份验证和权限控制 |
| 可维护性 | 是否便于后续扩展      |
| 可验证性 | 是否定义测试和验收标准   |

以代码生成为例：

| 评价维度  | 评价内容       |
| ----- | ---------- |
| 语法正确性 | 代码能否正常解析   |
| 功能正确性 | 是否实现需求     |
| 边界处理  | 是否考虑异常输入   |
| 可读性   | 命名和结构是否清晰  |
| 测试结果  | 是否通过相关测试   |
| 安全性   | 是否存在明显安全问题 |

注意：模型的自我评价不能代替真实测试。对于代码、数据和业务结果，应该尽可能结合外部验证工具。

### **3.4.5 Python 实现：技术方案反思助手**

示例文件规划：

`examples/chapter03/reflection.py`

整体流程：

1. 根据需求生成初始技术方案。
2. 使用独立评价 Prompt 检查方案。
3. 生成具体修改意见。
4. 根据修改意见优化方案。
5. 达到迭代次数上限后输出结果。

核心代码：

```
def generate_solution(requirement):    prompt = f"""    根据以下需求设计技术方案：    {requirement}    请输出系统架构、核心模块和技术选型。    """    return ask_deepseek(prompt)def reflect_solution(solution):    prompt = f"""    请从完整性、正确性、可行性和安全性四个维度    评价下面的技术方案：    {solution}    请列出存在的问题和具体改进建议。    """    return ask_deepseek(prompt)def refine_solution(solution, feedback):    prompt = f"""    请根据以下反馈修改技术方案：    原方案：    {solution}    改进意见：    {feedback}    输出优化后的完整方案。    """
```

执行逻辑：

```
def run_reflection(requirement, max_iterations=2):    solution = generate_solution(requirement)    for index in range(max_iterations):        feedback = reflect_solution(solution)        solution = refine_solution(solution, feedback)        print("第", index + 1, "轮反思完成")    return solution
```

本示例展示 Reflection 的核心结构。实际系统应增加评价结果解析、质量阈值判断和终止条件，避免模型在没有明显收益的情况下反复修改。

### **3.4.6 Reflection 与普通润色的区别**

| 对比维度 | 普通润色   | Reflection |
| ---- | ------ | ---------- |
| 处理方式 | 直接修改内容 | 先评价，再反馈和修正 |
| 评价标准 | 通常较模糊  | 可以明确质量维度   |
| 反馈信息 | 不一定保留  | 明确记录问题和建议  |
| 执行轮次 | 通常一次   | 可以多轮       |
| 适用场景 | 文本优化   | 复杂结果质量改进   |

Reflection 的核心不在于重复调用模型，而在于建立一个相对明确的质量反馈闭环。

### **3.4.7 Reflection 的优点与局限**

优点：

1. 能够发现初始结果中的遗漏。
2. 可以围绕明确标准优化结果。
3. 适合复杂文本、方案和代码生成任务。
4. 可以积累评价记录，分析常见问题。

局限：

1. 反思结果本身也可能错误。
2. 模型可能重复提出相似建议。
3. 多轮修改会增加调用成本。
4. 可能出现越改越偏离原始需求的情况。
5. 缺少外部验证时，模型可能只是让错误结果看起来更合理。

**工程建议：**

Reflection 应尽可能结合外部评价器。例如代码执行测试、JSON Schema 校验、业务规则检查和人工审核。不要只依赖模型自我评价。

## **3.5 三种动态执行模式的对比与组合**

### **3.5.1 三种模式的整体比较**

| 模式               | 主要解决问题   | 核心机制       | 典型应用      |
| ---------------- | -------- | ---------- | --------- |
| ReAct            | 下一步应该做什么 | 推理、行动、观察循环 | 智能搜索、故障排查 |
| Plan-and-Execute | 复杂目标如何拆解 | 先规划，再逐步执行  | 软件开发、研究分析 |
| Reflection       | 如何提升结果质量 | 生成、评价、修正   | 代码生成、方案评审 |

三种模式并不是相互排斥的。

在复杂 Agent 系统中，完全可以组合使用。

### **3.5.2 ReAct + Reflection**

适合需要动态调用工具，同时需要检查执行结果的场景。

例如企业技术支持 Agent：

1. 接收用户故障描述。
2. 使用 ReAct 查询日志、配置和知识库。
3. 根据查询结果分析问题。
4. 使用 Reflection 检查诊断结论是否有充分依据。
5. 如果存在遗漏，继续查询。
6. 输出诊断报告。

### **3.5.3 Plan-and-Execute + ReAct**

适合目标复杂、执行路径存在不确定性的任务。

例如开发一个 AI 应用：

1. Planner 制定开发计划。
2. Executor 执行当前子任务。
3. 某个子任务需要动态探索时，调用 ReAct Agent。
4. ReAct 完成子任务并返回结果。
5. Planner 更新任务状态。
6. 继续执行后续任务。

### **3.5.4 Plan-and-Execute + Reflection**

适合对任务完成质量要求较高的场景。

例如自动生成项目技术方案：

1. Planner 将需求拆解为多个子任务。
2. Executor 分别生成各模块方案。
3. Reflection 检查每个模块的完整性和一致性。
4. 发现问题后修正对应模块。
5. 汇总为最终技术方案。

### **3.5.5 三种模式组合使用**

可以构建一个更加完整的动态 Agent：

三种模式的职责可以概括为：

- Plan-and-Execute：负责整体任务组织。
- ReAct：负责局部动态行动。
- Reflection：负责结果质量改进。

## **3.6 动态 Agent 的工程设计与风险控制**

动态 Agent 的灵活性来自模型决策，但这也意味着它比固定 Workflow 更需要工程约束。

### **3.6.1 最大执行轮数**

所有动态 Agent 都应该设置最大执行轮数。

例如：

```
def run_agent(max_steps=5):    for step in range(max_steps):        # 模型决策        # 工具执行        # 更新状态        pass    return "任务执行结束"
```

如果没有最大轮数，模型可能重复调用工具，导致执行成本失控。

### **3.6.2 执行预算**

除了执行轮数，还应设置：

- 最大 Token 消耗。
- 最大执行时间。
- 最大工具调用次数。
- 最大并发任务数量。
- 最大重试次数。

可以为每个任务建立预算对象：

```
budget = {    "max_steps": 10,    "max_tool_calls": 8,    "max_retries": 2,    "max_duration": 120}
```

### **3.6.3 状态管理**

动态 Agent 不能只依赖对话历史保存任务进度。

建议将关键执行状态结构化保存：

```
{
  "task_id": "task_001",
  "goal": "分析企业技术架构",
  "status": "running",
  "current_step": 2,
  "tool_calls": 3,
  "observations": [
    "已获取企业基本信息",
    "已获取行业技术资料"
  ],
  "errors": [],
  "final_result": null
}
```

这样可以支持：

- 执行过程追踪。
- 中断后恢复。
- 失败原因分析。
- 成本统计。
- 人工介入。

### **3.6.4 工具权限控制**

模型选择了工具，不代表它一定有权执行。

例如：

| 工具     | 权限级别 | 控制策略     |
| ------ | ---- | -------- |
| 搜索知识库  | 低风险  | 可以自动执行   |
| 查询业务数据 | 中风险  | 校验用户访问权限 |
| 修改业务数据 | 高风险  | 需要业务规则校验 |
| 删除文件   | 高风险  | 需要人工确认   |
| 发布代码   | 高风险  | 需要审批和测试  |

核心原则：

**LLM 决定可以提出行动建议，但程序必须拥有最终执行控制权。**

### **3.6.5 执行日志与可观测性**

建议记录以下信息：

| 字段          | 说明        |
| ----------- | --------- |
| task_id     | 任务标识      |
| agent_name  | Agent 名称  |
| step        | 当前执行轮次    |
| model       | 使用的模型     |
| action      | 模型选择的行动   |
| tool_name   | 工具名称      |
| tool_input  | 工具输入摘要    |
| observation | 工具返回摘要    |
| duration    | 执行耗时      |
| token_usage | Token 使用量 |
| status      | 执行状态      |
| error       | 错误信息      |

日志中不得记录 API Key、密码等敏感信息。

### **3.6.6 动态 Agent 的常见问题**

| 问题     | 产生原因     | 解决方法          |
| ------ | -------- | ------------- |
| 无限循环   | 缺少停止条件   | 最大轮数、预算控制     |
| 重复调用工具 | 状态没有更新   | 记录工具调用历史      |
| 工具选择错误 | 模型判断不准确  | 工具白名单、描述优化    |
| 计划无法执行 | 计划缺少依赖约束 | 计划结构化和前置校验    |
| 反思反复修改 | 评价标准不明确  | 设定质量阈值和最大迭代次数 |
| 结果不可信  | 缺少外部验证   | 测试、规则校验、人工审核  |
| 成本过高   | 调用次数过多   | 限制预算、缓存、模型分级  |

## **3.7 企业应用案例：智能技术问题诊断 Agent**

本节将三种模式组合，设计一个企业内部技术问题诊断 Agent。

### **3.7.1 业务背景**

企业员工经常遇到以下问题：

- 应用无法启动。
- 数据库连接失败。
- 接口返回错误。
- 系统运行速度变慢。
- 部署后服务不可用。

传统客服系统通常需要人工根据问题类型查询知识库。

现在希望构建一个智能技术诊断 Agent，能够：

1. 理解用户的问题。
2. 自动查询相关知识。
3. 根据结果动态选择后续操作。
4. 生成诊断方案。
5. 对诊断结果进行质量检查。

### **3.7.2 系统架构**

### **3.7.3 模式职责划分**

| 模式               | 负责内容            |
| ---------------- | --------------- |
| Plan-and-Execute | 将诊断任务拆解为多个子任务   |
| ReAct            | 根据查询结果动态选择工具    |
| Reflection       | 检查诊断结论和修复建议     |
| Workflow         | 管理固定的输入、输出和审批流程 |

### **3.7.4 业务执行示例**

用户输入：

> 我们的 FastAPI 服务部署后无法连接 MySQL，请帮我排查。

Agent 的执行过程：

**第一阶段：任务规划**

Planner 生成计划：

1. 查询数据库连接失败的常见原因。
2. 检查数据库连接配置。
3. 检查数据库服务状态。
4. 分析日志。
5. 形成诊断报告。

**第二阶段：动态诊断**

ReAct Agent 根据实际结果决定后续动作：

- 查询配置后发现数据库地址为 `localhost`。
- 进一步检查运行环境，发现应用部署在 Docker 容器中。
- 判断 `localhost` 指向容器自身，而不是 MySQL 容器。
- 查询知识库，找到容器网络连接配置方案。

**第三阶段：结果反思**

Reflection 检查：

- 是否有日志或配置作为依据？
- 是否解释了问题原因？
- 是否给出了可执行的修复建议？
- 是否存在未经验证的假设？

**第四阶段：输出结果**

生成诊断报告，说明问题原因、修改建议、验证步骤和风险提示。

实际系统中，如果需要修改配置或重启服务，应经过权限检查和必要的人工审批。

## **3.8 本章小结**

本章学习了三种动态 Agent 执行模式。

1. **ReAct**：通过推理、行动和观察循环，让 Agent 根据执行结果动态选择下一步。
2. **Plan-and-Execute**：先将复杂目标拆解为执行计划，再逐步完成任务，并根据情况重新规划。
3. **Reflection**：通过评价和反馈机制检查初始结果，并进行多轮修正。

三种模式的适用边界：

- ReAct 更适合需要动态探索和工具调用的任务。
- Plan-and-Execute 更适合目标明确但步骤复杂的任务。
- Reflection 更适合需要持续改进输出质量的任务。

实际企业系统通常不会只使用一种模式，而是将三种模式与 Workflow 结合。

**本章最重要的设计原则：**

不要让 Agent 为了动态而动态。只有当任务确实需要动态决策、复杂规划或质量反馈时，才引入相应的执行模式。
