# 第1章练习：Agent设计模式基础

## 练习目标

通过概念辨析、场景分析和代码观察，判断一个任务是否需要 Agent，并能解释模式选择依据。

## 练习一：概念辨析

请判断下列说法是否正确，并说明理由。

1. 只要应用调用了大语言模型，它就是 Agent。
2. Workflow 一定比 Agent 简单，因此不适合企业级系统。
3. Multi-Agent 一定比单 Agent 更聪明。
4. Prompt 可以代替工具层的权限校验。
5. Agent Loop 应该设置最大执行轮数或其他停止条件。
6. State 和 Memory 是完全相同的概念。

### 参考答案

1. 错。单次 LLM 调用不一定具有动态行动、观察和状态推进能力。
2. 错。Workflow 对确定性业务通常更易控制、测试和审计，也可以构建复杂企业系统。
3. 错。多 Agent 增加协作和通信成本，只有分工或并行收益明显时才值得采用。
4. 错。Prompt 是行为引导，权限必须在应用和工具执行层强制校验。
5. 对。需要防止循环、成本失控和无效重试。
6. 错。State 主要描述当前运行实例状态；Memory 主要保存后续可复用的信息，二者生命周期和语义不同。

## 练习二：架构选型

为下列场景选择更合适的初始方案，并说明理由。

| 场景 | 候选方案 |
|---|---|
| A. 将一段文本压缩为100字摘要 | 单次 LLM 调用 / Agent Loop / Multi-Agent |
| B. 每天固定时间读取订单、计算汇总并发送报表 | Workflow / Swarm / Debate |
| C. 用户提出开放式问题，系统需要查阅多个工具并根据结果决定下一步 | 单次 LLM / ReAct / 固定脚本 |
| D. 生成代码后必须运行测试、根据失败日志修复并再次测试 | 单次 LLM / 具备工具的 Agent 或 Workflow+Agent 节点 |
| E. 同时分析法律、财务和技术材料，三个领域有独立资料源与验收标准 | 单 Agent 或 Multi-Agent，需评估分工收益 |

### 参考思路

- A：单次 LLM 调用即可。
- B：Workflow 更合适，执行路径稳定。
- C：ReAct 或受控 Agent Loop。
- D：Workflow 编排测试闭环，并在错误分析或修复节点使用 Agent；也可以采用受控 Agent。
- E：可评估 Multi-Agent，但先验证各专业任务是否能独立执行，以及协调成本是否值得。

## 练习三：阅读并运行代码

运行 `examples/chapter01/agent_loop_demo.py` 与 `examples/chapter01/workflow_vs_agent.py`。

回答：

1. Agent Loop 中，工具结果存放在哪里？
2. 为什么工具执行由 Python 程序完成，而不是直接相信模型声称“工具已执行”？
3. 示例中的 `decide()` 为什么还不能算真正的 LLM 决策？
4. 如果工具连续返回空结果，应该增加哪些停止或失败处理机制？

### 参考思路

1. 示例存放在 `AgentState.observations`。
2. 模型只提出调用请求，应用程序负责真正执行工具并读取真实结果。
3. 它使用固定规则模拟决策，没有调用语言模型。
4. 可增加最大轮数、连续失败计数、超时、预算限制、重试策略和人工介入。

## 练习四：设计一个企业内部知识助手

业务要求：

- 员工可以自然语言提问。
- 系统能够检索内部知识库。
- 如果答案不足以解决问题，可以创建工单。
- 创建工单前必须展示内容并由员工确认。
- 记录每次检索和工单操作。

请提交：

1. 一张系统架构图。
2. 组件清单：LLM、Prompt、Tool、State、Memory、Guardrails。
3. 选择 Workflow、Agent 或混合架构，并解释原因。
4. 至少列出三个风险及对应控制措施。

### 参考设计

推荐采用 Workflow + 局部 Agent 的混合方案：

1. 输入校验与意图分类。
2. 知识检索节点。
3. 答案充分性评估。
4. 对疑难问题使用 Agent 补充检索或分析。
5. 生成工单草稿。
6. 人工确认后调用工单创建工具。
7. 记录审计日志并返回结果。

风险控制示例：

- 检索内容过期：显示来源和更新时间。
- 工单误创建：创建前人工确认，工具侧校验用户权限。
- 敏感数据泄露：检索权限过滤、日志脱敏和最小权限。
